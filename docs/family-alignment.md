# Family Alignment product, privacy, and operating contract

## Status and customer promise

Family Alignment is a free, private, structured review room for one immutable
saved Decision Compare version. It helps a project owner collect a small
family's reactions before an architect conversation. It is not a public poll,
chat, contact-capture tool, professional approval, consensus engine, or paid
entitlement.

The promise is deliberately narrow:

- one active room for one owner-scoped immutable comparison version;
- exactly seven days of availability from server-side creation;
- at most five distinct anonymous responses;
- a response can be updated only by the browser that retains its response
  secret;
- the owner sees bounded aggregate counts and reasons, never respondent
  identity; and
- only the owner's explicit Decision Compare selection is authoritative.

Family Alignment does not send email, SMS, or WhatsApp invitations. It does not
collect names, email addresses, phone numbers, free text, files, professional
credentials, or household contact graphs. The owner copies the one-time secret
URL and shares it through a channel they control.

Paid checkout and Decision Compare fulfillment remain independent and closed
unless their existing launch controls are opened. Creating, opening, or
answering a Family Alignment room must never create an order, mark an order
paid, grant fulfillment, or bypass a revoked entitlement.

## Roles and lifecycle

The authenticated project owner may create, read the aggregate summary for,
and revoke a room. An anonymous reviewer may read the redacted room and create
or update only their own structured response with a high-entropy response
secret generated by the client. A support or operator role is not part of v1.

```text
owner saves immutable two-scenario comparison version
  -> owner creates room idempotently
  -> server returns /align#<capability> once; room expires exactly seven days later
  -> reviewer opens /align without an account bootstrap and the client redeems
     the fragment through a credential-omitting constant-path JSON API
  -> reviewer sees the redacted A/B presentation
  -> reviewer creates one structured response and retains response secret locally
  -> same reviewer may update that response without consuming another slot
  -> owner refreshes aggregate summary
  -> owner may explicitly select A or B in Decision Compare
  -> owner revokes room, or server expiry closes it
  -> scheduled retention removes expired/revoked Family Alignment data only
```

Creation is allowed only for the project's current latest saved comparison.
Creating again for the same comparison returns the existing room metadata
without reissuing its secret URL. A later immutable comparison version can
create its own room, and an earlier version's room remains active and
discoverable until its own expiry or revocation. At most one immutable room
ever exists per comparison. A room cannot be extended, retargeted, reopened,
or have its cap changed.

## Reviewer response vocabulary

The public write surface accepts only these values:

| Field | Allowed values | Rule |
|---|---|---|
| `role` | `spouse`, `parent`, `sibling`, `advisor`, `other` | Exactly one |
| `preference` | `A`, `B`, `not_ready` | Exactly one |
| `confidence` | `high`, `medium`, `low` | Exactly one |
| `reasons` | `budget`, `space`, `parking`, `accessibility`, `future_expansion`, `construction_complexity` | One to three distinct values |

Unknown fields, duplicate reasons, free text, HTML, URLs, IDs, timestamps, or
values outside the allowlists are rejected. The UI must explain that the
response is anonymous to the family group, advisory to the owner, and editable
only from a browser that retains its local response secret.

The first valid write for a response secret creates one receipt. A repeat with
that same secret updates that receipt and does not consume another slot. The
sixth distinct secret cannot create a receipt, but a valid secret for one of
the existing five receipts can still update while the room is active. Capacity
must be enforced atomically in D1; a read-then-insert count is not sufficient.

## Minimum public projection

The anonymous read response is a purpose-built allowlist, never a serialization
or shallow copy of an owner comparison, project, selection, report, or order.
It contains only:

- opaque room identifier, creation time and comparison version number;
- expiry time, current response count, and maximum response count of five;
- room state needed to render active, full, or closed behavior; and
- exactly two redacted scenario presentations with neutral A/B aliases and the
  bounded, server-derived comparison facts explicitly allowlisted by the
  backend contract.

The public response and rendered page must not contain, including in hidden
markup, URLs, preload data, errors, analytics, or source maps:

- owner selection or recommendation;
- project ID, project name, account ID, email, or other owner identity;
- internal scenario, comparison, selection, snapshot, order, or payment IDs;
- raw project/scenario input, plot dimensions, locality, source hashes, rules
  input, or stored JSON passthrough;
- scenario or project notes, questions, free text, files, or upload metadata;
- response tokens, token hashes, participant identities, individual receipts,
  or per-person timestamps; or
- paid, checkout, entitlement, provider, refund, or dispute state.

The owner read returns the selected room, its owner-only summary, and at most 20
rooms of bounded history; every listed room nests only that room's summary.
The summary is also allowlisted. It may return aggregate preference,
confidence, and reason counts plus one derived status:
`no_responses`, `split`, `leaning_a`, `leaning_b`, `aligned_a`, `aligned_b`, or
`not_ready`. It must not return a receipt list, response identifier, response
secret/hash, creation order, raw response, per-response timestamp, network
metadata, or a small-cell drill-down that reconstructs an individual.

## Secret, authorization, and browser boundaries

- Room access uses at least 256 bits of cryptographically random bearer
  material. Store only a one-way digest in D1 and return the raw value only in
  the successful first-create response.
- Newly created public URLs are exactly `/align#<43-character base64url
  capability>`. The fragment is available to the browser application but is
  not sent in the document request. Review read and write calls use the fixed
  paths `/api/shared/family-alignment` and
  `/api/shared/family-alignment/response`; the capability is accepted only in
  their exact, size-bounded JSON envelopes.
- The `/align` document and its API calls are authentication-free. The asset
  request is rebuilt as a clean `/index.html` request, and the client uses the
  anonymous API transport with `credentials: omit`, no authorization, no
  account cookies, and no CSRF header. GET and HEAD are `no-store`,
  `noindex,nofollow,noarchive`, and `no-referrer`; robots exclude `/align`.
  Because the document shares the account origin, a browser may still attach a
  matching ambient cookie to the initial top-level navigation. The Worker must
  ignore it: no session lookup occurs and no incoming credential is forwarded
  to the asset binding. A distinct cookieless hostname would be required to
  prevent the browser from sending that navigation cookie at all.
- Seven-day links issued before this transport change remain temporarily
  compatible through `/align/:token` and the legacy token-path APIs. A valid
  legacy document URL is immediately rewritten to `/align#token` without a
  reload, and the reviewer then uses only the fixed APIs. Operational logs
  template every legacy path. Remove these routes only after at least eight
  days, so every previously issued seven-day link has naturally closed.
- Automatic platform invocation logs remain disabled while legacy Family
  paths and Decision Share path capabilities exist. Application completion
  logs omit tokens, query, referrer, response body, and database error
  parameters.
- The public page must not load third-party scripts, pixels, fonts, images, link
  previews, or other requests that can receive the fragment. It must not place
  the capability in DOM attributes, analytics, errors, storage, print output,
  or a request URL. Terminal `404`/`410` states and printing scrub the fragment;
  transient dependency failure keeps it only so an explicit retry can work.
  Use the restrictive referrer policy and existing CSP boundary.
- Response secrets have the same entropy and digest-only storage requirement.
  Send them in the dedicated `x-family-response-token` header, never the URL or
  JSON body. Scope the digest to the room so a token from one room cannot
  address a response in another.
- The client stores one response secret and that reviewer's own structured
  choice locally per room so it can restore and edit the response. It must not
  put either value in application logs, analytics, error trackers, DOM
  attributes, copy controls, or owner APIs. Clearing this site's browser data
  removes the local copy and update capability; v1 has no recovery workflow.
- All owner routes require an authenticated session, trusted canonical origin,
  CSRF validation for mutations, owner scope at the query, and an
  ownership-safe `404` for foreign or missing resources.
- Public routes are bearer-authorized and rate limited without creating an
  identity profile. Missing or malformed secrets use one generic unavailable
  response. Known revoked, expired, and archived-project rooms return `410`
  without exposing owner/project details. A successful public read is admitted
  by one final D1 transaction immediately before disclosure; a dependency
  failure returns `503` without any room projection.

## Concurrency and failure semantics

These are release-blocking invariants:

1. Room creation is idempotent under retry and concurrency. At most one room
   exists for a comparison version, and an idempotency replay with
   different inputs is a conflict.
2. Creation verifies the saved comparison belongs to the authenticated owner,
   belongs to the named project, is immutable, is the project's current latest
   saved comparison and is still the intended input revision. A room cannot be
   retargeted after creation.
3. Receipt creation and the five-receipt cap are one atomic database decision.
   Concurrent sixth writers cannot both succeed or make the count exceed five.
4. An update proves possession of the room-scoped response secret and updates
   exactly one receipt. It cannot create a second receipt, take over another
   response, change rooms, or reopen an expired/revoked room.
5. Public-read admission re-evaluates revocation, database-time expiry, and the
   parent project's archive state in the same D1 transaction that increments
   the access counter. If closure wins, no comparison projection or open event
   is returned. If admission wins, that read may complete and every later read
   must observe closure. Missing or malformed stored expiry state and admission
   errors fail closed rather than treating the view counter as ancillary.
6. Expiry/revocation is re-evaluated at the write boundary. A response racing a
   revoke or expiry cannot commit after closure because of a stale application
   pre-read.
7. Summary counts come from committed receipts and always reconcile to a total
   from zero through five. No cache or analytics write is authoritative.
8. Room create/revoke and receipt create/update succeed or fail on their core
   D1 transaction. Best-effort aggregate analytics or logging may fail without
   turning a committed core action into a false `5xx`. The public-read access
   counter is the authoritative admission fence from invariant 5, not ancillary
   telemetry, so its failure returns `503` without disclosure.
9. Cleanup hard-deletes a room (and cascade-deletes its receipts) only after
   its expiry boundary or revocation time is more than 90 days old. It must not
   delete a project, comparison, selection, order, payment ledger, purchased
   snapshot, or public Decision Share. The 90-day closed-room window is still
   retained personal data for support/audit purposes, not anonymous analytics.

Stable reviewer client states distinguish `active`, `full`, `closed`, and
generic `unavailable`; expired, revoked, and archived `410` responses all map
to the same identity-safe `closed` screen. A dependency or authoritative
admission failure uses a distinct temporary state that confirms the review
remains private and retries the same bearer link; it must not ask for a link
that cannot be reissued for the same comparison. The success response
distinguishes `recorded` from `updated`. Retrying an accepted write must not
produce a duplicate receipt.

## Owner experience and trust copy

The owner view shows expiry, response count out of five, aggregate counts and
reasons, the derived summary status, copy-link on initial creation, refresh,
and revoke. It must state:

- “Family responses are advisory.”
- “Only your saved Decision Compare choice is authoritative.”
- “Reviewers cannot see your recommendation or choice.”
- “We do not ask reviewers for names, contact details, or comments.”

The owner must confirm revoke because it permanently closes the URL. The UI
must not imply that revocation deletes the immutable comparison or changes the
owner's selection. A room at zero responses has an intentional empty state; a
split or `not_ready` result must not be reframed as a recommendation.

## Accessibility acceptance

- Use a heading hierarchy and semantic `fieldset`/`legend` groups for role,
  preference, confidence, and reasons. Use native radio/checkbox controls or a
  fully equivalent keyboard and assistive-technology pattern.
- Announce loading, recorded, updated, validation failure, full, closed, and
  unavailable states with appropriate status/alert semantics without moving focus
  unexpectedly.
- All controls have visible focus, text labels, error association, and a
  minimum 48-by-48 CSS pixel target. Counts and A/B states are not conveyed by
  color alone.
- The complete reviewer and owner flows work with keyboard only, at 390 CSS
  pixels, at 200% zoom, with increased text spacing, and with reduced motion.
  Expiry is shown as an absolute date/time as well as relative copy so it is not
  an inaccessible countdown-only interaction.
- Print styles hide secrets, copy/revoke/submit controls, and local response
  status. The public document title and share metadata reveal no owner or
  project identity.

Screenshot inspection can identify visual hierarchy, reflow, and visible
states, but it cannot prove accessible names, keyboard order, announcements,
contrast ratios, storage behavior, or assistive-technology output. Those need
DOM, automated, and manual verification before release.

## Measurement and launch boundary

If implemented, measurement is server-emitted, daily aggregate-only, and
limited to `family_alignment_room_created`,
`family_alignment_review_opened`,
`family_alignment_response_submitted`, and
`family_alignment_room_revoked`. The backend emits at most one relevant event
after the token/auth boundary and core action have succeeded; the browser must
not emit a duplicate. Storage contains only the allowlisted event name,
allowlisted surface (`owner_compare` or `family_review`), bounded outcome, day,
count, and update time. It must never store room,
project, comparison, scenario, receipt, user, or token values;
role/preference/confidence/reasons; IP/user-agent; free text; or client
timestamps. Until an event is explicitly allowlisted and tested, neither
client nor server emits it.

The first release is an invited, synthetic-or-consented trial. Its retained
measurement can support only daily action totals for room creation, public
open, accepted response submissions (creates and updates combined), and
revocation. Ratios between those totals are directional operational signals,
not a room funnel: retries, repeat opens, and response updates make the
populations different.

V1 deliberately cannot calculate created-room-to-first-response conversion,
median response time, rooms reaching three or five receipts, response update
rate, expiry with zero responses, or owner selection after a family response.
Those require linkable room timelines or additional bounded aggregate events
that are not in the approved schema. Product reporting must label them
unavailable rather than infer them from action totals. Adding any such measure
requires a new privacy review, explicit retention decision, migration, and
tests before collection begins.

No conversion metric justifies weakening the redaction, bearer-secret,
five-receipt, professional-boundary, or paid-entitlement invariants. A single
cross-owner exposure, token leak, response takeover, cap overrun, or Family
Alignment action granting paid access is a release-blocking SEV-1.

The fragment-transport release changes no product data or measurement schema.
Its primary release KPI is **100% of newly issued room URLs using `/align#…`
and 100% of first-party reviewer requests using the two fixed API paths**.
Guardrails are zero capabilities in HTTP URLs, document/asset requests,
referrers, logs, analytics, DOM/print output, or authenticated bootstrap; zero
ambient cookies/authorization/CSRF on the fixed reviewer APIs and clean internal
app-shell asset fetches; unchanged seven-day legacy-link
availability; and byte/semantic-equivalent D1 admission, five-receipt,
revocation, archive, expiry, and retention behavior. Existing aggregate opens
and accepted-response totals remain directional adoption signals only.

No migration is required: capability digests, room rows, receipts, triggers,
and retention stay unchanged. Rolling back to the immediately prior Worker is
data-safe but cannot render fragment links created after this release because
that client expects a path token. Roll forward to the fragment-aware Worker to
restore access; never duplicate the capability into a path or query as a
rollback workaround.
